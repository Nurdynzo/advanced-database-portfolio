## 1. Case study: Lodgely

Lodgely is a real-estate operations platform built as microservices on MongoDB, RabbitMQ and Redis. The portfolio focuses on one slice of it: **facility management and rent payments**.

| | |
|---|---|
| **What the system does** | Property-management companies register buildings and units, lease units to tenants, bill rent per cycle, collect payments through a gateway (Paystack), withdraw collected funds, and control maintenance spending against budgets. |
| **Users** | Organisation owners and admins, facility managers, finance staff, tenants, and the payment gateway (system user). |
| **Main data** | Organisations, users, buildings, unit categories, units, staff assignments, tenancies, billing cycles, payments, payment allocations, payouts, budgets, budget lines, requisitions and requisition items. |
| **Key operations** | Lease a unit without double-letting it; bill each cycle; record a gateway payment exactly once; allocate payments to the oldest arrears first; compute tenant and building balances; request payouts; approve requisitions within budget. |

The production system is document-based (MongoDB). Portfolios 1–3 rebuild this slice in **PostgreSQL** to study what a relational model enforces; Portfolios 4–5 return to **MongoDB** and compare.

> **Data and confidentiality:** every dataset in this repository is fictional and generated by the scripts. No Lodgely source code, configuration, credentials or customer data is included.

## 3. Portfolio summaries

| # | Activity | Marks | What it demonstrates |
|---|---|---:|---|
| 1 | Database design and modelling | 7 | 16-table PostgreSQL schema in BCNF; ER diagram; normalisation from an unnormalised record to BCNF; range **exclusion constraint** blocking overlapping leases; composite foreign keys; balances computed as views instead of stored totals |
| 2 | Query processing and optimisation | 7 | Six real query patterns timed with `EXPLAIN ANALYZE` on ~700,000 payments, before and after: partial and covering indexes, trigram (`pg_trgm`) search, keyset pagination, a materialised view, and a query rewrite where indexes did not help |
| 3 | Transactions and concurrency | 7 | Atomicity (COMMIT, ROLLBACK, error, SAVEPOINT); a payment **double credit** reproduced with two sessions and fixed; write skew rejected under **SERIALIZABLE**; deadlock detection |
| 4 | NoSQL and advanced data models | 7 | MongoDB document model with embedding decisions, `$jsonSchema`/`$expr` validators, multi-document transactions, aggregation pipelines, TTL and text indexes; Redis key-value patterns; suitability comparison with the relational model |
| 5 | Distributed and cloud databases | 6 | Three-member MongoDB replica set: stale reads and write concerns, primary crash and re-election with no lost writes, transactional outbox with a change-stream relay, shard-key discussion, CAP |

### Key results from my runs

| Portfolio | Result |
|---|---|
| 2 | Building wallet 49.30 → 0.67 ms; user search 223.29 → 0.46 ms; overdue report 2,071.55 → 8.97 ms (indexes alone: no improvement); deep pagination 1,578.87 → 2.06 ms; reconciliation 421.50 → 0.16 ms; arrears dashboard 19,101.79 → 0.06 ms; inserts about 12% slower |
| 3 | Two concurrent confirmations credited one ₦200,000 payment as ₦400,000; SERIALIZABLE rejected the second budget approval (SQLSTATE 40001); PostgreSQL detected and broke a deadlock (40P01) |
| 4 | Validators enforced in-document rules, but MongoDB accepted a tenancy for a non-existent building; collection scan examined 100,004 documents vs 200 with an index; the unsafe confirmation pattern double-credited on MongoDB too |
| 5 | A frozen secondary served a stale read; a `w:3` write timed out yet was saved on the primary; after `podman kill` on the primary, `mongo2` was elected and all 100 majority-acknowledged writes survived; fire-and-forget lost 3 of 3 events while the outbox delivered 4 of 4 |

Each portfolio's README explains the method and analysis in full.

## 5. How to reproduce

There are two ways to run everything; both produce the same results.

### Option A — GUI tools (how the evidence in this repository was produced)

| Portfolio | Steps |
|---|---|
| 1 | Create database `lodgely` in pgAdmin. In the Query Tool run `01_schema.sql`, `02_sample_data.sql`, then `pgadmin/03_constraint_tests_pgadmin.sql`. Generate the diagram with **ERD For Database**. |
| 2 | Run `01_schema.sql` (Portfolio 1), then `pgadmin/01_seed_large_data_pgadmin.sql`, `VACUUM ANALYZE;`, `pgadmin/02_timing_report.sql`, `SELECT lodgely.record_timings('before');`, `pgadmin/03_optimisations_pgadmin.sql`, `VACUUM ANALYZE;`, `SELECT lodgely.record_timings('after');`, then `SELECT * FROM lodgely.timing_comparison;` |
| 3 | Run `pgadmin/00_reset_pgadmin.sql`, then `pgadmin/02_atomicity_pgadmin.sql`. For the concurrency demos, open two Query Tool tabs and follow section 10 of the Portfolio 3 README, resetting before each demo. |
| 4 | Start the containers: `podman run -d --name p4-mongo -p 27017:27017 docker.io/library/mongo:8.0 --replSet rs0 --bind_ip_all` and `podman run -d --name p4-redis -p 6379:6379 docker.io/library/redis:7.4`. Connect Compass to `mongodb://localhost:27017/?directConnection=true`, run `rs.initiate({_id: "rs0", members: [{_id: 0, host: "localhost:27017"}]})` in its shell, then paste `01`–`04` `.js` files in order. Run `python3 05_concurrency_mongo.py` and `python3 06_redis_keyvalue.py`. Finish with `podman stop p4-mongo p4-redis`. |
| 5 | Create network `rsnet`, start `mongo1`–`mongo3` with `podman run`, wait until `mongo1` answers, run `rs.initiate` with the three members, then follow the consistency and failover commands in the Portfolio 5 README. Run `python3 04_outbox_change_stream.py`. |

### Option B — one script per portfolio

From the repository root, with PostgreSQL running (`createdb lodgely` once) and, for 4–5, the containers started with `podman compose up -d` in that folder:

```bash
bash portfolio-1-database-design/run_all.sh
bash portfolio-2-query-optimisation/run_all.sh
bash portfolio-3-transactions-concurrency/run_all.sh
bash portfolio-4-nosql/run_all.sh                 # then: podman compose down (frees port 27017)
bash portfolio-5-distributed-cloud/run_all.sh
```

Each script checks its prerequisites first, explains what is missing, and writes its outputs to that portfolio's `evidence/` folder.
