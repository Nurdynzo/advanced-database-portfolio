# Portfolio 2 — Query Processing and Optimisation

This portfolio measures six realistic Lodgely queries and two application access patterns on a large dataset, then optimises each one and measures again. Each problem was chosen because it mirrors a performance risk found in the original (MongoDB-based) system, re-expressed against the relational schema from Portfolio 1.

## 1. Method

| Item | Detail |
|---|---|
| Database | PostgreSQL 16, schema from `../portfolio-1-database-design/01_schema.sql` |
| Data | Fictional, generated by `01_seed_large_data.sql` with a fixed random seed |
| Volume | 100k users, 1,000 buildings, 10k units, 60k tenancies, 710k billing cycles, ~700k payments, ~675k allocations, 69k payouts |
| Measurement | `EXPLAIN (ANALYZE, BUFFERS)`; each query is run once silently first so before and after are both measured with a warm cache |
| App patterns | Python + psycopg, median of 5 runs, optionally with simulated network latency per round trip |
| Machine | *(fill in: CPU, RAM, OS)* |

A dataset this size matters: on a few hundred rows every query is fast and the planner picks sequential scans anyway, so no optimisation would show a measurable effect.

**Reproduce everything:**

```bash
createdb lodgely
pip install "psycopg[binary]"
./run_all.sh          # rebuilds the database and writes all evidence/ files (~1–3 minutes)
```

## 2. Results summary

| # | Query | Before | After | Speed-up | What fixed it |
|---|---|---:|---:|---:|---|
| Q1 | Building wallet balance | 7.19 ms | 0.50 ms | ~14× | B-tree on `tenancy(unit_id)` + partial covering index on succeeded payments |
| Q2 | User substring search | 65.8 ms | 0.06 ms | ~1,100× | Trigram GIN indexes |
| Q3 | Overdue report, one building | 656.9 ms | 1.96 ms | ~335× | **Query rewrite** (indexes alone: 620 ms) |
| Q4 | Payment history, page 25,001 | 340.2 ms | 0.08 ms | ~4,500× | Matching index (186 ms), then **keyset pagination** |
| Q5 | Pending-payment reconciliation | 68.8 ms | 0.04 ms | ~1,900× | Partial index on pending rows |
| Q6 | Platform arrears dashboard | 665.2 ms | 0.03 ms | — | Materialised view (cost moved to a 0.54 s refresh) |
| W1 | Insert 50,000 payments | 381 ms | 441 ms | **16% slower** | Price paid: more indexes to maintain |

All figures are execution times from `evidence/02_baseline_plans.txt` and `evidence/04_optimised_plans.txt`.

## 3. Query-by-query analysis

### Q1 — Building wallet balance

**Before (7.19 ms):** the plan contained `Seq Scan on tenancy (rows=60000)`. The only index on `tenancy.unit_id` was the GiST index behind the overlap-exclusion constraint from Portfolio 1, and the planner did not use it for a plain equality join. It read all 60,000 tenancies to find the 60 belonging to building 500. Payments were fetched by `tenancy_id` and then filtered on `status`.

**Fix:**

- A B-tree index on `tenancy(unit_id)`.
- A partial covering index `payment(tenancy_id) INCLUDE (amount) WHERE status = 'succeeded'`.

**After (0.50 ms):** the tenancy lookup became an `Index Scan using ix_tenancy_unit`. The payment step became an `Index Only Scan ... Heap Fetches: 0`: the sum is computed entirely from the index, which contains only the rows the wallet cares about.

**Lesson:** an index created for a constraint is not automatically a good index for queries.

### Q2 — User search by substring

**Before (65.8 ms):** `ILIKE '%ade4321%'` has no fixed prefix, so a B-tree is useless. The plan was a `Seq Scan` with `Rows Removed by Filter: 99999`, meaning every user was checked to return one. This mirrors the original system's unanchored regex search.

**Fix:** `pg_trgm` GIN indexes on `email` and `full_name`. A trigram index breaks text into 3-character pieces, so any substring of 3+ characters can be looked up.

**After (0.06 ms):** a `BitmapOr` of two `Bitmap Index Scan`s, one per column, which is exactly the shape of the `OR` condition.

**Trade-off:** the two trigram indexes add 6.6 MB, and search terms shorter than 3 characters still need a scan.

### Q3 — Overdue report for one building

This is the most instructive result.

**Before (656.9 ms):** the query used the `v_cycle_balance` view from Portfolio 1. The plan shows `GroupAggregate ... rows=34733` over a `Merge Left Join ... rows=710000`. PostgreSQL computed the balance of **every billing cycle on the platform**, then joined the result to the 60 tenancies of building 500.

The building filter could not be pushed inside the view. It applies to `unit`, which is joined *outside* the view's `GROUP BY`, and the planner cannot move a filter on another table into an aggregate.

**Indexes alone (620 ms):** adding indexes barely changed anything (`Q3a` in the evidence). The plan stayed the same because the problem was the query's structure, not missing access paths.

**Fix:** rewrite the query to start from the building, reach its tenancies and their past-due cycles through indexes, and aggregate only those 710 cycles (`HAVING` replaces the view's balance filter).

**After (1.96 ms):** a chain of `Nested Loop`s over index scans, aggregating 710 rows instead of 710,000.

**Lesson:** views are a good tool for correctness (Portfolio 1 uses them to avoid stored totals), but they can hide work from the planner. In a hot path, write the query against the base tables.

### Q4 — Deep pagination

**Before (340.2 ms):** `ORDER BY initiated_at DESC ... OFFSET 500000` with no matching index. The plan shows `Sort Method: external merge Disk: ~39 MB`: the sort did not fit in memory and spilled to disk.

**Index only (185.9 ms):** an index on `(initiated_at DESC, payment_id DESC)` removed the sort, but the plan still reads `rows=500020` from the index and discards 500,000 of them. `OFFSET` always walks past every skipped row, so the cost grows linearly with page depth.

**Fix:** keyset (cursor) pagination, `WHERE (initiated_at, payment_id) < (last_ts, last_id) ... LIMIT 20`. The index seeks directly to the cursor and reads 20 rows.

**After (0.08 ms):** constant cost at any page depth.

**Trade-off:** keyset pages allow "next" and "previous" but not "jump to page 25,001". `payment_id` is included as a tie-breaker so that rows with identical timestamps are never skipped or repeated. The original system's transaction history already used keyset pagination; this measurement shows why that was a good choice.

### Q5 — Pending-payment reconciliation

**Before (68.8 ms):** a `Parallel Seq Scan` over ~700k payments to find ~1,500 pending ones.

**Fix:** partial index `payment(initiated_at) WHERE status = 'pending'`.

**After (0.04 ms):** an `Index Scan` that returns the oldest 100 rows already in order, with no sort. The index is only **56 kB**, compared with 21 MB for a full index on the same column, because it stores only the 0.2% of rows the query ever asks for.

### Q6 — Platform arrears dashboard

**Before (665.2 ms):** aggregates all 710,000 cycles every time the dashboard loads. No index can avoid this, because the query genuinely needs every row.

**Fix:** a materialised view `mv_building_arrears` that stores the per-building result.

**After (0.03 ms):** reading 1,000 pre-computed rows.

**Trade-off:** the work did not disappear; it moved. `REFRESH MATERIALIZED VIEW CONCURRENTLY` took 0.54 s, and between refreshes the dashboard shows stale data (the view's `refreshed_at` column makes this visible). This is acceptable for a management dashboard refreshed every few minutes. It is **not** acceptable for a tenant's own balance, which is why Q3 was fixed with a rewrite instead.

## 4. Application-level patterns (`05_app_patterns.py`)

| Pattern | Round trips | Local socket | With 2 ms per round trip |
|---|---:|---:|---:|
| Tenancy list, N+1 queries | 61 | 1.76 ms | 132.0 ms |
| Tenancy list, single JOIN | 1 | 0.46 ms | 2.55 ms |
| Platform income, fetch 675k rows + sum in app | 1 | 410 ms | 395 ms |
| Platform income, `SUM()` in database | 1 | 175 ms | 168 ms |

**N+1:** on a local socket the N+1 version looks harmless (1.8 ms). With a realistic 2 ms per round trip, which is optimistic for a call to another microservice over HTTP, it becomes **52× slower** than the JOIN, and the cost grows with every tenancy in the building. `EXPLAIN` cannot reveal this because each of the 61 queries is individually fast. In the original system, the equivalent lookups cross a service boundary, so a batched lookup (one request for all IDs) is the microservice equivalent of the JOIN.

**Fetch-all:** transferring 675,267 rows to sum them in the application was 2.3× slower than `SUM()`, and it uses application memory proportional to the platform's entire payment history. For one building the difference is negligible. The danger is that this pattern scales with history size, so it gets steadily worse without any code change.

## 5. Costs of optimisation

| Cost | Evidence |
|---|---|
| **Storage** | The `payment` table is 72 MB; its indexes total 125 MB. The new indexes added 69 MB in total. |
| **Write speed** | Inserting 50,000 payments went from 381 ms to 441 ms (+16%), because every insert now also updates `ix_payment_initiated` and `ix_payment_pending`. The partial `ix_payment_tenancy_succeeded` was not touched, since the test rows were `pending`, which is a side benefit of partial indexes. |
| **Freshness** | The materialised view is stale between refreshes; each refresh costs ~0.5 s. |
| **Maintenance** | Every index must be justified by a query. An index that no query uses only adds write and storage cost. |

`payment` is write-heavy (every gateway callback inserts or updates a row), so each payment index was chosen for a specific, frequent query, and two of the three are partial to keep them small.

## 6. Key takeaways

1. **Measure before optimising.** Q1 looked fine at 7 ms; the plan still revealed a full scan that would grow with the data.
2. **Indexes are not always the answer.** Q3 needed a rewrite and Q6 needed pre-computation. Indexes alone left Q3 at 620 ms.
3. **Partial and covering indexes** give large gains for a fraction of the storage (Q1, Q5).
4. **Some problems live outside the database** (N+1, fetch-all) and only show up when measured from the application.
5. **Every optimisation has a price** in storage, write speed or freshness. Choose based on how the data is read and written.
